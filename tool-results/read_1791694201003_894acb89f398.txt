    12→## 0. Executive summary (1-minute version)
    13→DNS = the Internet's phonebook: a global, distributed lookup service that translates human-memorable names (shop.example) into the numbers (IP addresses) the network actually routes on. It is worth a film because it is *invisible by design*: it usually answers in single-digit to tens of milliseconds (NDSS 2026 measurement: 1.6 ms cached / 8 ms uncached average, see §3), so users never notice it — until it breaks, and whole companies (Facebook, Oct 2021) or large parts of the consumer Internet (Dyn DDoS, 2016) disappear. Most counter-intuitive point (the film's hook): when you press Enter, your browser does not know where shop.example lives — no machine on the Internet is named "shop.example" — and the answer isn't stored in one place either. It is assembled on the fly by a hierarchy of servers that each know only one small piece ("ask the next counter down the hall"), then cached on sticky notes (TTLs) that expire. The name→number split is a deliberate 1983 design decision (Paul Mockapetris, RFC 882/883) to replace one hand-maintained text file (HOSTS.TXT at SRI-NIC) that was already choking on a few thousand hosts — a system that today answers trillions of queries a day on public resolvers alone (Cloudflare's 1.1.1.1: average 1.9 trillion/day per Cloudflare's Feb 27, 2025 Radar post, now verified from the primary source; Google Public DNS: over 1 trillion/day as of 2018 — see §7).

    15→## 1. Situation & the mystery
    16→**Names vs addresses.** Humans use names (shop.example); routers and machines use IP addresses. "Each device connected to the Internet has a unique IP address … DNS translates domain names to IP addresses so browsers can load Internet resources." DNS servers "eliminate the need for humans to memorize IP addresses such as 192.168.1.1 (in IPv4), or more complex newer alphanumeric IP addresses … (in IPv6)."
    17→- Cloudflare Learning Center, "What is DNS?": https://www.cloudflare.com/learning/dns/what-is-dns/ (★★, official vendor documentation)
    18→- The Internet's routing layer never sees "shop.example": the name must become an IP address before any packet (envelope) can be addressed and sent. (Consistent with RFC 1034 model: "The Internet uses … names … [resolved into] resource information such as addresses"; film phrasing.)
    19→
    20→**The first millisecond after Enter.** When the user hits Enter, the browser does NOT know the address. Lookup order (modern stack, uncached worst case):
    21→1. Browser's own DNS cache (Chrome: visible at chrome://net-internals/#dns).
    22→2. The OS "stub resolver" (a.k.a. DNS client) — the "second and last local stop before a DNS query leaves your machine"; it checks its own cache, then sends a query with the *recursive flag set* to a recursive resolver (usually the ISP's, or a chosen public one like 1.1.1.1).
    23→3. Recursive resolver (the "DNS recursor"): if it doesn't have the answer cached, it walks the hierarchy root → TLD → authoritative, then hands the final IP back; the browser can finally address its first packet.
    24→- Source for the full chain and the 8-step uncached walkthrough: Cloudflare "What is DNS?" (8 steps listed verbatim: user types → recursive resolver → root → TLD → domain's nameserver → back), incl. "The example below outlines all 8 steps when nothing is cached." https://www.cloudflare.com/learning/dns/what-is-dns/
    25→- Cloudflare on the stub resolver: "The process inside your operating system that is designed to handle this query is commonly called a 'stub resolver' or DNS client … If it does not [have the record cached], it then sends a DNS query (with a recursive flag set), outside the local network to a DNS recursive resolver inside the Internet service provider (ISP)." https://www.cloudflare.com/learning/dns/what-is-dns/
    26→- Visual note for the film: at t=0 the browser holds an addressed-but-blank envelope with no destination — it can't even put a number on it. The name is NOT the address; until translation completes, no packet can leave. (Metaphor consistent with EP1's envelope motif.)

    28→## 2. Origins & key milestones
    29→**The HOSTS.TXT era (pre-1983).** Before DNS, the ARPANET kept ONE master text file, HOSTS.TXT, mapping host names → numerical addresses. It was maintained by the Stanford Research Institute's Network Information Center (SRI-NIC); Elizabeth Feinler's team ran the ARPANET directory (and later the Host Naming Registry, 1972–1989). Number assignment itself (the "Assigned Numbers List") was Jon Postel's job at USC's Information Sciences Institute.
    30→- Wikipedia "Domain Name System", History section: "The Stanford Research Institute (now SRI International) maintained a text file named HOSTS.TXT that mapped host names to the numerical addresses of computers on the ARPANET … Addresses were assigned manually. Computers … were added to the primary file by contacting the SRI Network Information Center (NIC) … via telephone during business hours." https://en.wikipedia.org/wiki/Domain_Name_System
    31→- **RFC 608, "Host Names On-Line" (M.D. Kudlick, SRI-ARC, dated January 10, 1974)** ★★★: proposes the NIC maintain an online ASCII file of host names/addresses/attributes, generated weekly ("run periodically (weekly, or as the situation warrants)") from a source file "designed and maintain[ed]" by Jake Feinler at the NIC. Full text fetched 2026-10-11 (re-verified this session; header reads "NIC # 21256  January 10, 1974"): https://www.rfc-editor.org/rfc/rfc608.txt
    32→  - ⚠️ Date correction: the brief said "RFC 608 (1973)"; the RFC's own header says **January 10, 1974**. Use 1973→1974 carefully on screen (options: "1974" or "early-1970s").
    33→- Scale limit narrative: admins emailed changes to HOSTMASTER@SRI-NIC; every host pulled the whole file via FTP from SRI-NIC; "by the early 1980s, maintaining a single, centralized host table had become slow and unwieldy and the emerging network required an automated naming system" (Wikipedia DNS, History). https://en.wikipedia.org/wiki/Domain_Name_System
    34→  - The "phone-book floppy mailed out" image: the standard popular-history line is that early host tables were distributed as printed RFCs / mailed media before/alongside FTP distribution. 【to verify — exact "floppy disk mailing" citation; RFC 810/812 era HOSTS.TXT was fetched via FTP from SRI-NIC.     36→**Mockapetris creates DNS (1983).** Postel handed Paul Mockapetris the job of forging a compromise between five competing naming proposals; Mockapetris instead invented the Domain Name System (at USC Information Sciences Institute).
    37→- Wikipedia DNS History: "Postel directed the task of forging a compromise between five competing proposals of solutions to Paul Mockapetris.     41→- BIND, the first Unix name-server implementation, was written in 1984 by four UC Berkeley students (Douglas Terry, Mark Painter, David Riggle, Songnian Zhou), substantially revised 1985 by Kevin Dunlap (DEC). https://en.wikipedia.org/wiki/Domain_Name_System ; ISC history: https://www.isc.org/binders/

    43→**The DNS we still run (1987).** **RFC 1034 ("Domain Names — Concepts and Facilities") and RFC 1035 ("Implementation and Specification"), November 1987** ★★★ superseded RFC 882/883 and are *still* the core DNS specs today (38+ years). Both fetched & header dates re-verified this session (1034: "Obsoletes: RFCs 882, 883, 973 … November 1987"). https://www.rfc-editor.org/rfc/rfc1034 ; https://www.rfc-editor.org/rfc/rfc1035
    44→- RFC 1035 fixed the classic DNS message format incl. the 512-byte UDP payload limit (verbatim from fetched text: "Messages carried by UDP are restricted to 512 bytes (not counting the IP header …)"). ★★★
    45→
    46→**Root servers: 13 letters, A–M.** There are exactly 13 logical root identities, named a.root-servers.net … m.root-servers.net.
    47→- Why 13: a DNS reply over UDP had to fit 512 bytes unfragmented; a root reply contains the NS records + A records (glue) for every root server, and 13 is what fits. Wikipedia (re-fetched this session): "The choice of 13 name servers was made because of limitations in the original DNS specification, which specifies a maximum packet size of 512 bytes when using the User Datagram Protocol (UDP). Technically however, fourteen name servers fit into an IPv4 packet." https://en.wikipedia.org/wiki/Root_name_server
    48→- Anycast: "all operate in multiple geographical locations using a routing technique called anycast addressing". **Actual root server instances: 2,047 operational as of 2026-10-11** ★★★ — from root-servers.org itself (page fetched this session carries the self-updating line: "As of 2026-10-11T03:30:24Z, the root server system consists of 2047 operational instances operated by the 12 independent root server operators. The 13 root name servers are operated by 12 independent organisations."). https://root-servers.org/ (film-safe phrasing: "13 identities, ~2,000 physical instances"). [Historical note for timeline shots: 1,954 as of 2025-12-05 per Wikipedia citing the same source.]
    49→- Ten of the 13 were originally in the US; I (Stockholm), K (Amsterdam), M (Tokyo) abroad. Operators incl. Verisign (A, J), USC-ISI (B), Cogent (C), University of Maryland (D), NASA Ames (E), ISC (F), US DoD DISA (G), US Army Research Lab (H), Netnod (I), RIPE NCC (K), ICANN (L), WIDE Project (M). Operator table re-verified this session from both Wikipedia (re-fetched) and root-servers.org ("Verisign, Inc." listed first for A; 12 operators for 13 letters because Verisign runs A and J). https://en.wikipedia.org/wiki/Root_name_server
    50→- Bootstrapping circularity: resolvers seed the root addresses from a small "root hints" file — needed to solve "you need DNS to find DNS". Wikipedia: https://en.wikipedia.org/wiki/Root_name_server

    52→## 3. How it works
    53→**Two roles.** The DNS world splits into *recursive resolvers* (do the walking for you) and *authoritative servers* (hold the actual records). Cloudflare's framing: "the recursive resolver is at the beginning of the DNS query and the authoritative nameserver is at the end."
    54→- "Authoritative DNS server = a server that actually holds, and is responsible for, DNS resource records … can satisfy queries from its own data without needing to query" others. https://www.cloudflare.com/learning/dns/what-is-dns/
    55→- "Recursive DNS resolver = the computer that responds to a recursive request from a client and takes the time to track down the DNS record … making a series of requests until it reaches the authoritative DNS nameserver for the requested record (or times out …)." https://www.cloudflare.com/learning/dns/what-is-dns/
    56→
    57→**The four-hop walk (uncached).** Cloudflare's canonical walkthrough, "8 steps … when nothing is cached" — film uses shop.example in place of example.com:
    58→1. User types the name; the stub resolver sends a recursive query to a DNS recursive resolver.
    59→2. Resolver queries a **root nameserver** (.) — root replies only with: "here are the servers for the .example TLD" (a *referral*).
    60→3. Resolver queries the **TLD server** (.example) — it replies only with the address of the domain's **authoritative nameservers**.
    61→4. Resolver queries the **authoritative nameserver** for shop.example — it finally returns the A/AAAA record (the IP address), which the resolver passes back to the client.
    62→- Verbatim 8-step list: https://www.cloudflare.com/learning/dns/what-is-dns/ ("The 8 steps in a DNS lookup")
    63→- Key teaching point (Cloudflare's own library analogies): root = "an index in a library that points to different racks of books"; TLD = "a specific rack of books"; authoritative = "a dictionary on a rack of books"; recursor = "a librarian who is asked to go find a particular book". Same URL.
    64→- Query types along the way: recursive query (client→resolver: give me the answer or an error) vs iterative query (resolver→each server: best answer/referral). "A typical uncached DNS lookup will involve both recursive and iterative queries." Same URL.
    65→- Referrals: root/TLD servers don't know the final answer; they each only answer "who to ask next". (Root: "answers other requests by returning a list of the authoritative name servers for the appropriate top-level domain (TLD)" — Wikipedia Root name server: https://en.wikipedia.org/wiki/Root_name_server)
    66→
    67→**Record types (the cards the servers exchange).** (Definitions below verified verbatim against the fetched RFC texts this session.)
    68→- **A** (type 1): "a host address" — maps a name to a 32-bit IPv4 address. RFC 1035 §3.2.2 ("A 1 a host address") ★★★ https://www.rfc-editor.org/rfc/rfc1035
    69→- **AAAA** (type 28): "stores a single IPv6 address … A 128 bit IPv6 address is encoded in the data portion". RFC 3596 (October 2003) ★★★ https://www.rfc-editor.org/rfc/rfc3596
    70→- **CNAME** (type 5): "the canonical name for an alias" — one name points to another name; the resolver then restarts the lookup for the canonical name. RFC 1035 §3.2.2 ★★★ (e.g., www.shop.example → shop.example → A record)
    71→- Also defined in RFC 1035 §3.2.2: NS (2), SOA (6, "marks the start of a zone of authority"), PTR (12), MX (15). ★★★

    78→**Latency (how long a lookup takes).**
    79→- **Peer-reviewed measurement (NDSS 2026, paper PDF fetched & verified this session):** "While cached domain names take on average **1.6 ms** to resolve, uncached take **8 ms**. With DNSSEC, the latencies become even larger, taking around **20 ms**, due to signature validation for each response." — Weissteiner, Czerny, Franza, Gast, Ullrich, Gruss, "Continuous User Behavior Monitoring using DNS Cache Timing Attacks", NDSS Symposium 2026 (San Diego, Feb 23–27, 2026; TU Graz / SBA Research) ★★★ https://hannesweissteiner.com/pdfs/dmt.pdf (DOI 10.14722/ndss.2026.242287). Caveat: measured on a local systemd-resolved setup with a fast forwarder — the *full* root→TLD→authoritative walk from a cold resolver can cost more.
    80→- A typical full (uncached, cold) lookup takes on the order of **20–120 ms**; cached answers are ~1 ms or less (local cache hits).     81→- Film-safe framing: "a warm cache answers in about a millisecond; a cold, full walk costs tens to ~100 ms — roughly a blink of an eye is 100–400 ms, so even worst-case DNS is well inside a blink."

    83→## 4. Caching & TTL
    84→**Cache layers (closest first).** 1) browser cache ("the first location checked for the requested record"; Chrome exposes it at chrome://net-internals/#dns), 2) OS stub resolver cache ("the second and last local stop before a DNS query leaves your machine"), 3) the recursive resolver's cache (shared by all its users), 4) upstream: TLD/authoritative servers see only a fraction of the world's queries because resolvers cache. Cloudflare: https://www.cloudflare.com/learning/dns/what-is-dns/ (caching section).
    85→- Resolver shortcuts from cache: "If the resolver does not have the A records, but does have the NS records for the authoritative nameservers, it will query those name servers directly, bypassing several steps… If the resolver does not have the NS records, it will send a query to the TLD servers (.com in our case), skipping the root server." Same URL.
    86→
    87→**TTL — the expiry label on every record.** RFC 1035 (primary, verbatim quote re-verified against fetched text this session): "TTL a 32 bit signed integer that specifies the time interval that the resource record may be cached before the source of the information should again be consulted. Zero values are interpreted to mean that the RR can only be used for the transaction in progress, and should not be cached." ★★★ https://www.rfc-editor.org/rfc/rfc1035
    88→- TTL is set by the zone owner (the record's publisher), not by the resolver; each cache along the path counts down its own copy from whatever remained when it arrived. (RFC 1035 semantics; standard explanation.)
    89→- Negative answers (NXDOMAIN) also get cached — "negative caching" — governed by the SOA record's fields per RFC 2308 (March 1998; header date re-verified this session) ★★★ https://www.rfc-editor.org/rfc/rfc2308
    90→
    91→**"DNS propagation" is really cache expiry.** Changing a record doesn't get pushed anywhere; old copies simply live in caches until their TTLs run out, then the next query re-fetches the new value. So the honest sentence is: a change is *visible everywhere* after at most the old TTL, not after a mystical "propagation time".
    92→- Corroborating explanations: DigiCert glossary "What is DNS propagation?" ("Whether or not an ISP ignores TTL in DNS records, TTL values still affect propagation") https://www.digicert.com/glossary/what-is-dns-propagation ; powerdmarc.com "DNS propagation refers to the time it takes for a DNS change to become visible across the internet, as caching…" https://powerdmarc.com/what-is-dns-propagation/ (★). Cloudflare's old "what is DNS propagation" learning page now 404s — do not cite its URL on screen.
    93→- TTL values in the wild: commonly anywhere from 5 minutes to 24 hours (300 s … 86,400 s). benjojo: "A lot of providers in the wild will set their DNS TTL's from anywhere from 5 mins, to a hour" https://blog.benjojo.co.uk/post/just-how-long-do-dns-resolvers-cache-last (★, measurement post) ; common recommendation 1–24 h = 3,600–86,400 s https://dev.to/atennoncini/what-is-dns-ttl-time-to-live-2i3 (★).
    94→- Practical rule: if your TTL is 3600 s (1 h), cached copies may serve the old number for up to an hour after you change it. (Derived from RFC 1035 semantics.)
    95→- Live demo of TTL expiry (from the Facebook outage): "By 15:50 UTC, Facebook's domains had expired from the caches in all major public resolvers" — ~11 minutes after their nameservers went dark, the world's caches stopped answering facebook.com (Wikipedia, 2021 Facebook outage, citing public-resolver data: https://en.wikipedia.org/wiki/2021_Facebook_outage). Caches didn't just hide the failure — they briefly *delayed* it, then flipped it to SERVFAIL once TTLs ran out.

    97→## 5. The fragile side
    98→**DNS hijacking / wildcard redirection — VeriSign SiteFinder (2003).** Between **15 September 2003 and 4 October 2003**, VeriSign (operator of the .com/.net registries) installed a wildcard record so that EVERY unregistered .com/.net name resolved — to VeriSign's own ad portal. (All details below re-verified this session from the re-fetched Wikipedia article.)
    99→- "Site Finder was a wildcard DNS record for all .com and .net unregistered domain names … All Internet users who accessed any unregistered domains in the .com and .net domain space were redirected to a VeriSign web portal … It had the effect of capturing the web traffic for several million mistyped or experimental web accesses per day." Wikipedia (well-sourced) https://en.wikipedia.org/wiki/Site_Finder
   100→- Why it broke things: NXDOMAIN ("no such name") is a *signal* — spam filters, mail servers and other software rely on it; SiteFinder turned "name doesn't exist" into "here's a web server", so "the redirection broke various RFCs and disrupted existing Internet services, such as email relay and filtering (spam filters were not able to detect the validity of domain names)". Same URL.
   101→- Traffic effect: verisign.com jumped from ~2,500th most popular site (Alexa) into the top 20 (top 10 during the controversy). Same URL.
   102→- Community reaction: ISC shipped a BIND patch so ISPs could filter the wildcard; the IAB published a technical critique; on **4 October 2003** VeriSign disabled Site Finder after a formal ICANN letter; ICANN's SSAC later (July 9, 2004) concluded registries should phase out such wildcard use. Same URL + ICANN advisory https://www.icann.org/en/system/files/correspondence/btw-lynn-to-lynn-15sep03-en.htm (caveat: ICANN site reorganized; verify URL before citing on screen 【to verify】).
   103→- The DNS-jacking lesson: whoever controls the lookup layer controls where names go — even for names that don't exist.
   104→
   105→**DNSSEC — signing the phonebook.** DNS answers are unsigned by default: any on-path attacker (rogue Wi-Fi, hijacked resolver) can forge an answer and send you to the wrong IP. DNSSEC adds a chain of digital signatures from the root down to the record.
   106→- Core spec trio: **RFC 4033, RFC 4034, RFC 4035 (March 2005; header dates re-verified this session)** ★★★ https://www.rfc-editor.org/rfc/rfc4033 (4034/4035 same series). What DNSSEC adds: "cryptographic authentication of data, authenticated denial of existence, and data integrity, but not availability or confidentiality" (Wikipedia DNSSEC, re-fetched: https://en.wikipedia.org/wiki/Domain_Name_System_Security_Extensions). I.e., it proves the answer is genuine and complete, but doesn't hide it or guarantee the server stays up.
   107→- **The root zone itself was signed on 15 July 2010**, completing the top link of the chain of trust: "DNSSEC was first deployed at the root level on July 15, 2010"; the first full production signed root zone carries SOA serial 2010071501; by May 2010 all thirteen root servers were already serving the Deliberately-Unsignable Root Zone (Wikipedia DNSSEC, re-fetched this session). ★★ https://en.wikipedia.org/wiki/Domain_Name_System_Security_Extensions (root signing ceremonies run by ICANN/Verisign). Net effect: 1983→2010 — DNS ran unsigned for its first ~27 years.
   108→- Cost: bigger responses (signatures), more work; measured uncached lookups take ~20 ms with DNSSEC vs ~8 ms without in one peer-reviewed measurement (Weissteiner et al., NDSS 2026 ★★★ — see §3).
   109→- **Adoption, 2026 (both verified this session):** (a) **≈94% of delegated TLDs are signed** — own count of the live root zone file (internic.net/domain/root.zone, fetched 2026-10-11): 1,351 of the 1,438 delegated TLDs carry DS records ★★★; (b) **≈40% of the world's users sit behind DNSSEC-validating resolvers** — APNIC Labs DNSSEC measurement, World (XA), as of 2026-10-09: 1-day average 39.9%, 10-day average 39.7%, 30-day average 39.2% (JSON time series fetched) ★★★ dataset https://stats.labs.apnic.net/dnssec/XA . Wikipedia's summary (re-fetched): "As of 2026, DNSSEC deployment is spotty" — because signing a domain is still opt-in for individual domain owners even where the TLD is signed.
   110→
   111→**Encrypting the question — DoT and DoH.** Classic DNS is plaintext UDP: anyone on the path can read every name you look up (and forge answers). Two IETF fixes:
   112→- **DoT — DNS over TLS, RFC 7858 (May 2016)**: DNS wrapped in a TLS session; dedicated port 853. Verified from the RFC's own header fetched this session ("May 2016"; authors Z. Hu, L. Zhu, J. Heidemann, A. Mankin, D. Wessels, P. Hoffman): https://www.rfc-editor.org/rfc/rfc7858 ★★★
   113→- **DoH — DNS Queries over HTTPS, RFC 8484 (October 2018)**: DNS queries inside ordinary HTTPS traffic on port 443 — invisible to network middleboxes, which made it popular with browsers and controversial with network admins. Verified from the RFC's own header fetched this session ("October 2018"; authors P. Hoffman, P. McManus): https://www.rfc-editor.org/rfc/rfc8484 ★★★
   114→- Both are live in the major public resolvers (Google Public DNS and 1.1.1.1 support DoT and DoH — endpoints listed on their service pages; Google's endpoint https://dns.google/dns-query, Cloudflare's https://cloudflare-dns.com/dns-query).

   116→## 6. Real cases & failure modes
   117→**Case 1 — Facebook vanishes (October 4, 2021): a BGP mistake became a DNS blackout.** During routine maintenance, a configuration command withdrew Facebook's routes *including the routes to its own DNS servers*. (Cloudflare's post and BOTH Facebook engineering posts were fetched & quote-verified this session — see Appendix note 2 for the live URLs.)
   118→- Cloudflare's real-time forensic account ("Understanding how Facebook disappeared from the Internet", published 2021-10-04) ★★★ https://blog.cloudflare.com/october-2021-facebook-outage/ :
   119→  - "At around **15:40 UTC** we saw a peak of routing changes from Facebook. … Routes were withdrawn, Facebook's DNS servers went offline … With those withdrawals, Facebook and its sites had effectively disconnected themselves from the Internet."
   120→  - Effect on DNS: "Due to Facebook stopping announcing their DNS prefix routes through BGP, our and everyone else's DNS resolvers had no way to connect to their nameservers. Consequently, 1.1.1.1, 8.8.8.8, and other major public DNS resolvers started issuing (and caching) SERVFAIL responses."
   121→  - Duration (DNS availability of facebook.com on 1.1.1.1): unavailable from ~**15:50 UTC** to ~**21:20 UTC** (≈5.5 h); renewed BGP activity ~21:00, peaked 21:17, "as of 21:28 UTC Facebook appears to be reconnected to the global Internet and DNS working again".
   122→  - Second-order effect: "a tsunami of additional DNS traffic" — apps and users kept retrying; 1.1.1.1 saw **~30x more queries than usual** for facebook.com/whatsapp.com.
   123→  - Nice line for the film: "one minute after the problem occurred, Cloudflare engineers were in a room wondering why 1.1.1.1 couldn't resolve facebook.com and worrying that it was somehow a fault with our systems."

   125→  - "On October 4, 2021, at **15:39 UTC**, the social network Facebook and its subsidiaries … became globally unavailable for a period of **six to seven hours**."
   126→  - Root cause per Facebook's own posts (now live, verified verbatim): "During one of these routine maintenance jobs, **a command was issued with the intention of assessing the availability of global backbone capacity, which unintentionally took down all the connections in our backbone network, effectively disconnecting Facebook data centers globally**. Our systems are designed to audit commands like these to prevent mistakes like this, but a bug in that audit tool prevented it from properly stopping the command." (Wikipedia, re-fetched.)
