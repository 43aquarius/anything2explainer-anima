    11→## 0. Executive summary (1-minute version)
    12→DNS = the Internet's phonebook: a global, distributed lookup service that translates human-memorable names (shop.example) into the numbers (IP addresses) the network actually routes on. It is worth a film because it is *invisible by design*: it usually answers in tens of milliseconds, so users never notice it — until it breaks, and whole companies (Facebook, Oct 2021) or large parts of the consumer Internet (Dyn DDoS, 2016) disappear. Most counter-intuitive point (the film's hook): when you press Enter, your browser does not know where shop.example lives — no machine on the Internet is named "shop.example" — and the answer isn't stored in one place either. It is assembled on the fly by a hierarchy of servers that each know only one small piece ("ask the next counter down the hall"), then cached on sticky notes (TTLs) that expire. The name→number split is a deliberate 1983 design decision (Paul Mockapetris, RFC 882/883) to replace one hand-maintained text file (HOSTS.TXT at SRI-NIC) that was already choking on a few thousand hosts — a system that today answers trillions of queries a day on public resolvers alone (Cloudflare's 1.1.1.1: average 1.9 trillion/day per Feb 2025 Cloudflare blog; Google Public DNS: over 1 trillion/day as of 2018 — see §7).

    14→## 1. Situation & the mystery
    15→**Names vs addresses.** Humans use names (shop.example); routers and machines use IP addresses. "Each device connected to the Internet has a unique IP address … DNS translates domain names to IP addresses so browsers can load Internet resources." DNS servers "eliminate the need for humans to memorize IP addresses such as 192.168.1.1 (in IPv4), or more complex newer alphanumeric IP addresses … (in IPv6)."
    16→- Cloudflare Learning Center, "What is DNS?": https://www.cloudflare.com/learning/dns/what-is-dns/ (★★, official vendor documentation)
    17→- The Internet's routing layer never sees "shop.example": the name must become an IP address before any packet (envelope) can be addressed and sent. (Consistent with RFC 1034 model: "The Internet uses … names … [resolved into] resource information such as addresses"; film phrasing.)
    18→
    19→**The first millisecond after Enter.** When the user hits Enter, the browser does NOT know the address. Lookup order (modern stack, uncached worst case):
    20→1. Browser's own DNS cache (Chrome: visible at chrome://net-internals/#dns).
    21→2. The OS "stub resolver" (a.k.a. DNS client) — the "second and last local stop before a DNS query leaves your machine"; it checks its own cache, then sends a query with the *recursive flag set* to a recursive resolver (usually the ISP's, or a chosen public one like 1.1.1.1).
    22→3. Recursive resolver (the "DNS recursor"): if it doesn't have the answer cached, it walks the hierarchy root → TLD → authoritative, then hands the final IP back; the browser can finally address its first packet.
    23→- Source for the full chain and the 8-step uncached walkthrough: Cloudflare "What is DNS?" (8 steps listed verbatim: user types → recursive resolver → root → TLD → domain's nameserver → back), incl. "The example below outlines all 8 steps when nothing is cached." https://www.cloudflare.com/learning/dns/what-is-dns/
    24→- Cloudflare on the stub resolver: "The process inside your operating system that is designed to handle this query is commonly called a 'stub resolver' or DNS client … If it does not [have the record cached], it then sends a DNS query (with a recursive flag set), outside the local network to a DNS recursive resolver inside the Internet service provider (ISP)." https://www.cloudflare.com/learning/dns/what-is-dns/
    25→- Visual note for the film: at t=0 the browser holds an addressed-but-blank envelope with no destination — it can't even put a number on it. The name is NOT the address; until translation completes, no packet can leave. (Metaphor consistent with EP1's envelope motif.)

    27→## 2. Origins & key milestones
    28→**The HOSTS.TXT era (pre-1983).** Before DNS, the ARPANET kept ONE master text file, HOSTS.TXT, mapping host names → numerical addresses. It was maintained by the Stanford Research Institute's Network Information Center (SRI-NIC); Elizabeth Feinler's team ran the ARPANET directory (and later the Host Naming Registry, 1972–1989). Number assignment itself (the "Assigned Numbers List") was Jon Postel's job at USC's Information Sciences Institute.
    29→- Wikipedia "Domain Name System", History section: "The Stanford Research Institute (now SRI International) maintained a text file named HOSTS.TXT that mapped host names to the numerical addresses of computers on the ARPANET … Addresses were assigned manually. Computers … were added to the primary file by contacting the SRI Network Information Center (NIC) … via telephone during business hours." https://en.wikipedia.org/wiki/Domain_Name_System
    30→- **RFC 608, "Host Names On-Line" (M.D. Kudlick, SRI-ARC, dated January 10, 1974)** ★★★: proposes the NIC maintain an online ASCII file of host names/addresses/attributes, generated weekly ("run periodically (weekly, or as the situation warrants)") from a source file "designed and maintain[ed]" by Jake Feinler at the NIC. Full text fetched 2026-10-11: https://www.rfc-editor.org/rfc/rfc608.txt
    31→  - ⚠️ Date correction: the brief said "RFC 608 (1973)"; the RFC's own header says **January 10, 1974**. Use 1973→1974 carefully on screen (options: "1974" or "early-1970s").
    32→- Scale limit narrative: admins emailed changes to HOSTMASTER@SRI-NIC; every host pulled the whole file via FTP from SRI-NIC; "by the early 1980s, maintaining a single, centralized host table had become slow and unwieldy and the emerging network required an automated naming system" (Wikipedia DNS, History). https://en.wikipedia.org/wiki/Domain_Name_System
    33→  - The "phone-book floppy mailed out" image: the standard popular-history line is that early host tables were distributed as printed RFCs / mailed media before/alongside FTP distribution. 【to verify — exact "floppy disk mailing" citation; RFC 810/812 era HOSTS.TXT was fetched via FTP from SRI-NIC. Do NOT put "mailed floppies" on screen without a source; "one file, one NIC, phone calls to change it" is verified.】

    35→**Mockapetris creates DNS (1983).** Postel handed Paul Mockapetris the job of forging a compromise between five competing naming proposals; Mockapetris instead invented the Domain Name System (at USC Information Sciences Institute).
    36→- Wikipedia DNS History: "Postel directed the task of forging a compromise between five competing proposals of solutions to Paul Mockapetris. Mockapetris instead created the Domain Name System in 1983 while at the USC Information Sciences Institute." https://en.wikipedia.org/wiki/Domain_Name_System
    37→- **RFC 882 ("Domain Names: Concepts and Facilities") and RFC 883 ("Implementation and Specification"), November 1983** ★★★ — the original DNS specs (now Obsolete, superseded). https://www.rfc-editor.org/rfc/rfc882 ; https://www.rfc-editor.org/rfc/rfc883 (dates verified via rfc-editor info pages & Wikipedia DNS)
    38→- Mockapetris's own retrospective (primary source): P. Mockapetris & K. Dunlap, "Development of the Domain Name System", ACM SIGCOMM 1988 (Computer Communication Review) — recounts HOSTS.TXT's growth problems and the design goals. Bibliographic entries verified: https://dl.acm.org/doi/10.1145/52325.52338 ; PDF mirror: https://www.cs.arizona.edu/sites/default/files/pdfs/development_of_the_domain_name_system.pdf (also hosted at cs.princeton.edu course archives) ★★★
    39→- "Five competing proposals": before DNS, several naming schemes were on the table (hierarchical/flat/centralized designs); Postel tasked Mockapetris with finding the compromise, and he created DNS instead (Wikipedia DNS History, citing the SIGCOMM paper).
    40→- BIND, the first Unix name-server implementation, was written in 1984 by four UC Berkeley students (Douglas Terry, Mark Painter, David Riggle, Songnian Zhou), substantially revised 1985 by Kevin Dunlap (DEC). https://en.wikipedia.org/wiki/Domain_Name_System ; ISC history: https://www.isc.org/binders/
    41→
    42→**The DNS we still run (1987).** **RFC 1034 ("Domain Names — Concepts and Facilities") and RFC 1035 ("Implementation and Specification"), November 1987** ★★★ superseded RFC 882/883 and are *still* the core DNS specs today (38+ years). https://www.rfc-editor.org/rfc/rfc1034 ; https://www.rfc-editor.org/rfc/rfc1035
    43→- RFC 1035 fixed the classic DNS message format incl. the 512-byte UDP payload limit ("Messages carried using UDP are restricted to 512 bytes … longer messages are truncated"). ★★★
    44→
    45→**Root servers: 13 letters, A–M.** There are exactly 13 logical root identities, named a.root-servers.net … m.root-servers.net.
    46→- Why 13: a DNS reply over UDP had to fit 512 bytes unfragmented; a root reply contains the NS records + A records (glue) for every root server, and 13 is what fits. Wikipedia: "The choice of 13 name servers was made because of limitations in the original DNS specification, which specifies a maximum packet size of 512 bytes when using UDP. Technically however, fourteen name servers fit into an IPv4 packet." https://en.wikipedia.org/wiki/Root_name_server
    47→- Anycast: "all operate in multiple geographical locations using a routing technique called anycast addressing" — actual root server **instances: 1954 as of 2025-12-05** (Wikipedia, citing root-servers.org data). https://en.wikipedia.org/wiki/Root_name_server ; current count: https://root-servers.org/ (film-safe phrasing: "13 identities, ~1,900+ physical instances" or "1,000+").
    48→- Ten of the 13 were originally in the US; I (Stockholm), K (Amsterdam), M (Tokyo) abroad. Operators incl. Verisign (A, J), USC-ISI (B), Cogent (C), University of Maryland (D), NASA (E), ISC (F), US DoD (G), US Army Research Lab (H), Netnod (I), RIPE NCC (K), ICANN (L), WIDE (M). https://en.wikipedia.org/wiki/Root_name_server
    49→- Bootstrapping circularity: resolvers seed the root addresses from a small "root hints" file — needed to solve "you need DNS to find DNS". Wikipedia: https://en.wikipedia.org/wiki/Root_name_server

    51→## 3. How it works
    52→**Two roles.** The DNS world splits into *recursive resolvers* (do the walking for you) and *authoritative servers* (hold the actual records). Cloudflare's framing: "the recursive resolver is at the beginning of the DNS query and the authoritative nameserver is at the end."
    53→- "Authoritative DNS server = a server that actually holds, and is responsible for, DNS resource records … can satisfy queries from its own data without needing to query" others. https://www.cloudflare.com/learning/dns/what-is-dns/
    54→- "Recursive DNS resolver = the computer that responds to a recursive request from a client and takes the time to track down the DNS record … making a series of requests until it reaches the authoritative DNS nameserver for the requested record (or times out …)." https://www.cloudflare.com/learning/dns/what-is-dns/
    55→
    56→**The four-hop walk (uncached).** Cloudflare's canonical walkthrough, "8 steps … when nothing is cached" — film uses shop.example in place of example.com:
    57→1. User types the name; the stub resolver sends a recursive query to a DNS recursive resolver.
    58→2. Resolver queries a **root nameserver** (.) — root replies only with: "here are the servers for the .example TLD" (a *referral*).
    59→3. Resolver queries the **TLD server** (.example) — it replies only with the address of the domain's **authoritative nameservers**.
    60→4. Resolver queries the **authoritative nameserver** for shop.example — it finally returns the A/AAAA record (the IP address), which the resolver passes back to the client.
    61→- Verbatim 8-step list: https://www.cloudflare.com/learning/dns/what-is-dns/ ("The 8 steps in a DNS lookup")
    62→- Key teaching point (Cloudflare's own library analogies): root = "an index in a library that points to different racks of books"; TLD = "a specific rack of books"; authoritative = "a dictionary on a rack of books"; recursor = "a librarian who is asked to go find a particular book". Same URL.
    63→- Query types along the way: recursive query (client→resolver: give me the answer or an error) vs iterative query (resolver→each server: best answer/referral). "A typical uncached DNS lookup will involve both recursive and iterative queries." Same URL.
    64→- Referrals: root/TLD servers don't know the final answer; they each only answer "who to ask next". (Root: "answers other requests by returning a list of the authoritative name servers for the appropriate top-level domain (TLD)" — Wikipedia Root name server: https://en.wikipedia.org/wiki/Root_name_server)
    65→
    66→**Record types (the cards the servers exchange).**
    67→- **A** (type 1): "a host address" — maps a name to a 32-bit IPv4 address. RFC 1035 §3.2.2 ★★★ https://www.rfc-editor.org/rfc/rfc1035
    68→- **AAAA** (type 28): "stores a single IPv6 address … A 128 bit IPv6 address is encoded in the data portion". RFC 3596 (October 2003) ★★★ https://www.rfc-editor.org/rfc/rfc3596
    69→- **CNAME** (type 5): "the canonical name for an alias" — one name points to another name; the resolver then restarts the lookup for the canonical name. RFC 1035 §3.2.2 ★★★ (e.g., www.shop.example → shop.example → A record)
    70→- Also defined in RFC 1035 §3.2.2: NS (2), SOA (6), PTR (12), MX (15). ★★★
    71→
    72→**Public recursive resolvers (the ones ordinary people point at).**
    73→- **Google Public DNS**: announced **December 3, 2009** ("making the web faster and more secure"); addresses 8.8.8.8 and 8.8.4.4 (IPv6: 2001:4860:4860::8888 / ::8844), anycast-mapped; "As of 2018, it is the largest public DNS service in the world, handling over a trillion queries per day"; supports DoH/DoT and validates DNSSEC. Wikipedia (citing primary sources): https://en.wikipedia.org/wiki/Google_Public_DNS ; Google: https://developers.google.com/speed/public-dns
    74→- **Cloudflare + APNIC 1.1.1.1**: announced **April 1, 2018** — blog title "Introducing DNS Resolver, 1.1.1.1 (not a joke)" ★★★ https://blog.cloudflare.com/dns-resolver-1-1-1-1/ (published 2018-04-01). Addresses 1.1.1.1 and 1.0.0.1, "provided to Cloudflare by APNIC for both joint research and this service"; served by Cloudflare's global anycast network; stated goal: "the fastest public resolver on the planet while raising the standard of privacy protections for users". Wikipedia: https://en.wikipedia.org/wiki/1.1.1.1 ("The service was announced on April 1, 2018 … partnership with APNIC … functions as a recursive name server").

    76→**Latency (how long a lookup takes).**
    77→- A typical DNS lookup takes on the order of **20–120 ms** uncached; cached answers are ~1 ms or less (local cache hits). Secondary sources agree on the magnitude: Apposite Technologies "A typical DNS lookup might take 20 to 120 ms" https://www.apposite-tech.com/blog/dns-latency-testing/ (★); CleanBrowsing "A typical DNS resolution takes between 10–100 ms" https://cleanbrowsing.org/what-is-dns-latency/ (★); OneUptime "A normal cached DNS response should complete in under 1 ms; an uncached resolution … 50–200 ms" https://oneuptime.com/blog/dns-resolution-time/ (★).
    78→- Measured example from academic monitoring: cached names average **1.6 ms**, uncached **8 ms** (Weissteiner et al., "Continuous User Behavior Monitoring using DNS Cache", ARES/SBA 2020-ish) ★★ https://publications.sba-research.org (secondary fetch of abstract; exact paper details 【to verify】).
    79→- Film-safe framing: "a warm cache answers in about a millisecond; a cold, full walk costs tens to ~100 ms — roughly a blink of an eye is 100–400 ms, so even worst-case DNS is well inside a blink."

    81→## 4. Caching & TTL
    82→**Cache layers (closest first).** 1) browser cache ("the first location checked for the requested record"; Chrome exposes it at chrome://net-internals/#dns), 2) OS stub resolver cache ("the second and last local stop before a DNS query leaves your machine"), 3) the recursive resolver's cache (shared by all its users), 4) upstream: TLD/authoritative servers see only a fraction of the world's queries because resolvers cache. Cloudflare: https://www.cloudflare.com/learning/dns/what-is-dns/ (caching section).
    83→- Resolver shortcuts from cache: "If the resolver does not have the A records, but does have the NS records for the authoritative nameservers, it will query those name servers directly, bypassing several steps… If the resolver does not have the NS records, it will send a query to the TLD servers (.com in our case), skipping the root server." Same URL.
    84→
    85→**TTL — the expiry label on every record.** RFC 1035 (primary): "TTL a 32 bit signed integer that specifies the time interval that the resource record may be cached before the source of the information should again be consulted. Zero values are interpreted to mean that the RR can only be used for the transaction in progress, and should not be cached." ★★★ https://www.rfc-editor.org/rfc/rfc1035
    86→- TTL is set by the zone owner (the record's publisher), not by the resolver; each cache along the path counts down its own copy from whatever remained when it arrived. (RFC 1035 semantics; standard explanation.)
    87→- Negative answers (NXDOMAIN) also get cached — "negative caching" — governed by the SOA record's fields per RFC 2308 (March 1998) ★★★ https://www.rfc-editor.org/rfc/rfc2308
    88→
    89→**"DNS propagation" is really cache expiry.** Changing a record doesn't get pushed anywhere; old copies simply live in caches until their TTLs run out, then the next query re-fetches the new value. So the honest sentence is: a change is *visible everywhere* after at most the old TTL, not after a mystical "propagation time".
    90→- Corroborating explanations: DigiCert glossary "What is DNS propagation?" ("Whether or not an ISP ignores TTL in DNS records, TTL values still affect propagation") https://www.digicert.com/glossary/what-is-dns-propagation ; powerdmarc.com "DNS propagation refers to the time it takes for a DNS change to become visible across the internet, as caching…" https://powerdmarc.com/what-is-dns-propagation/ (★). Cloudflare's old "what is DNS propagation" learning page now 404s — do not cite its URL on screen.
    91→- TTL values in the wild: commonly anywhere from 5 minutes to 24 hours (300 s … 86,400 s). benjojo: "A lot of providers in the wild will set their DNS TTL's from anywhere from 5 mins, to a hour" https://blog.benjojo.co.uk/post/just-how-long-do-dns-resolvers-cache-last (★, measurement post) ; common recommendation 1–24 h = 3,600–86,400 s https://dev.to/atennoncini/what-is-dns-ttl-time-to-live-2i3 (★).
    92→- Practical rule: if your TTL is 3600 s (1 h), cached copies may serve the old number for up to an hour after you change it. (Derived from RFC 1035 semantics.)
    93→- Live demo of TTL expiry (from the Facebook outage): "By 15:50 UTC, Facebook's domains had expired from the caches in all major public resolvers" — ~11 minutes after their nameservers went dark, the world's caches stopped answering facebook.com (Wikipedia, 2021 Facebook outage, citing public-resolver data: https://en.wikipedia.org/wiki/2021_Facebook_outage). Caches didn't just hide the failure — they briefly *delayed* it, then flipped it to SERVFAIL once TTLs ran out.

    95→## 5. The fragile side
    96→**DNS hijacking / wildcard redirection — VeriSign SiteFinder (2003).** Between **15 September 2003 and 4 October 2003**, VeriSign (operator of the .com/.net registries) installed a wildcard record so that EVERY unregistered .com/.net name resolved — to VeriSign's own ad portal.
    97→- "Site Finder was a wildcard DNS record for all .com and .net unregistered domain names … All Internet users who accessed any unregistered domains in the .com and .net domain space were redirected to a VeriSign web portal … It had the effect of capturing the web traffic for several million mistyped or experimental web accesses per day." Wikipedia (well-sourced) https://en.wikipedia.org/wiki/Site_Finder
    98→- Why it broke things: NXDOMAIN ("no such name") is a *signal* — spam filters, mail servers and other software rely on it; SiteFinder turned "name doesn't exist" into "here's a web server", so "the redirection broke various RFCs and disrupted existing Internet services, such as email relay and filtering (spam filters were not able to detect the validity of domain names)". Same URL.
    99→- Traffic effect: verisign.com jumped from ~2,500th most popular site (Alexa) into the top 20 (top 10 during the controversy). Same URL.
   100→- Community reaction: ISC shipped a BIND patch so ISPs could filter the wildcard; the IAB published a technical critique; on **4 October 2003** VeriSign disabled Site Finder after a formal ICANN letter; ICANN's SSAC later (July 9, 2004) concluded registries should phase out such wildcard use. Same URL + ICANN advisory https://www.icann.org/en/system/files/correspondence/btw-lynn-to-lynn-15sep03-en.htm (caveat: ICANN site reorganized; verify URL before citing on screen 【to verify】).
   101→- The DNS-jacking lesson: whoever controls the lookup layer controls where names go — even for names that don't exist.
   102→
   103→**DNSSEC — signing the phonebook.** DNS answers are unsigned by default: any on-path attacker (rogue Wi-Fi, hijacked resolver) can forge an answer and send you to the wrong IP. DNSSEC adds a chain of digital signatures from the root down to the record.
   104→- Core spec trio: **RFC 4033, RFC 4034, RFC 4035 (March 2005)** ★★★ https://www.rfc-editor.org/rfc/rfc4033 (4034/4035 same series). What DNSSEC adds: "cryptographic authentication of data, authenticated denial of existence, and data integrity, but not availability or confidentiality" (Wikipedia DNSSEC: https://en.wikipedia.org/wiki/Domain_Name_System_Security_Extensions). I.e., it proves the answer is genuine and complete, but doesn't hide it or guarantee the server stays up.
   105→- **The root zone itself was signed on 15 July 2010**, completing the top link of the chain of trust: "DNSSEC was first deployed at the root level on July 15, 2010." Wikipedia DNSSEC, "Deployment at the DNS root" ★★ https://en.wikipedia.org/wiki/Domain_Name_System_Security_Extensions (root signing ceremonies run by ICANN/Verisign; primary: root-dnssec-2010 material). Net effect: 1983→2010 — DNS ran unsigned for its first ~27 years.
   106→- Cost: bigger responses (signatures), more work; measured uncached DNSSEC lookups ~20 ms vs ~8 ms without in one academic measurement (Weissteiner et al., ★★, same caveat as §3). Deployed on most TLDs today (Verisign/ICANN stats 【to verify】).
   107→
   108→**Encrypting the question — DoT and DoH.** Classic DNS is plaintext UDP: anyone on the path can read every name you look up (and forge answers). Two IETF fixes:
   109→- **DoT — DNS over TLS, RFC 7858 (May 2016)**: DNS wrapped in a TLS session; dedicated port 853. Verified from the RFC's own header ("May 2016", authors Hu/Heidemann/Wessels/Hoffman): https://www.rfc-editor.org/rfc/rfc7858 ★★★
   110→- **DoH — DNS Queries over HTTPS, RFC 8484 (October 2018)**: DNS queries inside ordinary HTTPS traffic on port 443 — invisible to network middleboxes, which made it popular with browsers and controversial with network admins. Verified from the RFC's own header ("October 2018", authors Hoffman/McManus): https://www.rfc-editor.org/rfc/rfc8484 ★★★
   111→- Both are live in the major public resolvers (Google Public DNS and 1.1.1.1 support DoT and DoH — endpoints listed on their service pages; Google's endpoint https://dns.google/dns-query, Cloudflare's https://cloudflare-dns.com/dns-query).

   113→## 6. Real cases & failure modes
   114→**Case 1 — Facebook vanishes (October 4, 2021): a BGP mistake became a DNS blackout.** During routine maintenance, a configuration command withdrew Facebook's routes *including the routes to its own DNS servers*.
   115→- Cloudflare's real-time forensic account ("Understanding how Facebook disappeared from the Internet", published 2021-10-04) ★★★ https://blog.cloudflare.com/october-2021-facebook-outage/ :
   116→  - "At around **15:40 UTC** we saw a peak of routing changes from Facebook. … Routes were withdrawn, Facebook's DNS servers went offline … With those withdrawals, Facebook and its sites had effectively disconnected themselves from the Internet."
   117→  - Effect on DNS: "Due to Facebook stopping announcing their DNS prefix routes through BGP, our and everyone else's DNS resolvers had no way to connect to their nameservers. Consequently, 1.1.1.1, 8.8.8.8, and other major public DNS resolvers started issuing (and caching) SERVFAIL responses."
   118→  - Duration (DNS availability of facebook.com on 1.1.1.1): unavailable from ~**15:50 UTC** to ~**21:20 UTC** (≈5.5 h); renewed BGP activity ~21:00, peaked 21:17, "as of 21:28 UTC Facebook appears to be reconnected to the global Internet and DNS working again".
   119→  - Second-order effect: "a tsunami of additional DNS traffic" — apps and users kept retrying; 1.1.1.1 saw **~30x more queries than usual** for facebook.com/whatsapp.com.
   120→  - Nice line for the film: "one minute after the problem occurred, Cloudflare engineers were in a room wondering why 1.1.1.1 couldn't resolve facebook.com and worrying that it was somehow a fault with our systems."
   121→- Wikipedia's consolidated account ("2021 Facebook outage") with the official Facebook engineering post as a source ★★ https://en.wikipedia.org/wiki/2021_Facebook_outage :
   122→  - "On October 4, 2021, at **15:39 UTC**, the social network Facebook and its subsidiaries … became globally unavailable for a period of **six to seven hours**."
   123→  - Root cause per Facebook's Oct 5 engineering post: "During maintenance, **a command was run to assess the global backbone capacity, and that command accidentally disconnected all of Facebook's data centers**. While Facebook's DNS servers ran on a separate network, they were **designed to withdraw their BGP routes if they could not connect to Facebook's data centers**." (This is the exact cascade: backbone → DNS withdrawal → unreachable.)
   124→  - Restoration: "Facebook gradually returned after a team got access to server computers at the Santa Clara, California, data center and reset them"; BGP restored ~21:50, DNS answers flowing again 22:05 UTC, services generally back by ~22:45–22:50 UTC.
   125→  - Third-party spillover: users fled to Twitter, Discord, Signal, Telegram — which suffered their own disruptions from the load.
   126→
   127→**Case 2 — Dyn DDoS (October 21, 2016): attack the phonebook, silence the speakers.** Three waves of DDoS against DNS provider Dyn took down a huge slice of the US/European consumer Internet for hours.
   128→- "On October 21, 2016, three consecutive distributed denial-of-service attacks were launched against the Domain Name System (DNS) provider Dyn. The attack caused major Internet platforms and services to be unavailable to large swathes of users in Europe and North America." Waves at **11:10–13:20, 15:50–17:00, 20:00–22:10 UTC**. Wikipedia (well-sourced): https://en.wikipedia.org/wiki/2016_Dyn_cyberattack
   129→- Mechanism: "numerous DNS lookup requests from tens of millions of IP addresses" — a botnet of hijacked IoT devices (**Mirai malware**: "printers, IP cameras, residential gateways and baby monitors") flooding Dyn's resolvers with junk lookups so real ones couldn't get through. Same URL.

   161→### 7.2 Analogies (5, with fit & distortion notes)
   162→
   163→1. **DNS = the Internet's phonebook (title metaphor).**
   164→   - Fit: names humans remember → numbers machines dial; you need the number *before* you can connect; the directory is organized (root → TLDs → domains) and mostly invisible to users. Wikipedia DNS uses it as its headline analogy ("An often-used analogy to explain the DNS is that it serves as the phone book for the Internet").
   165→   - Distortion: a paper phonebook is one complete local copy, printed yearly, same number for everyone; DNS is no single book — it's a hierarchy assembled per-query, different callers can get different answers (CDNs, geography), it changes in minutes, and you can't lose "the" book because there isn't one. Also: humans dial phones; here the machine dials, so users never see the number at all.
   166→2. **The four-counter referral office (stub → recursive → root → TLD → authoritative).**
   167→   - Fit: each clerk points you to the *right next counter* instead of knowing the answer (referrals); the recursive resolver is like a hired courier who does all the walking for you while you wait; the root is the front desk that only knows which department (TLD) handles ".example".
   168→   - Distortion: real offices have one front desk; DNS's front desk is 13 identities × ~1,900 anycast instances, and the whole "walk" takes tens of milliseconds. Bureaucracy never remembers; DNS's clerks write everything on sticky notes (see 3) — and the *courier* (recursive resolver) is shared by thousands of users, so one person's walk becomes everyone's answer.
   169→3. **Cache = sticky notes on the side of the monitor.**
   170→   - Fit: answers get written down where the next asker can see them ("shop.example = 192.0.2.33 — don't ask again"); closest note (browser) is fastest; notes make the system survivable (root servers would melt otherwise — see the 2003 survey stat that only 2% of root queries were legitimate [needs-update caveat, see Appendix]).
   171→   - Distortion: real notes serve one person; resolver caches are communal (one user's lookup warms the cache for thousands); notes can be *wrong* (spoofing) without looking wrong; and every DNS note carries its own countdown timer (TTL) — office notes don't usually expire on their own.
   172→4. **TTL = expiry-date label on a milk carton.**
   173→   - Fit: each cached answer is stamped with how long it stays trustworthy; after expiry, you must go back to the source. Explains "propagation": after you change the record, old milk sits in other people's fridges until its date passes — there is no recall mechanism.
   174→   - Distortion: TTL is a *maximum*, not a guarantee — caches may evict early (or, badly, hold longer; some resolvers misbehave); the label is set by the record's owner, but countdowns start fresh per cache as the record travels; and "expiry" doesn't mean the answer becomes *unsafe* — it just becomes *untrusted*.
   175→5. **You can't mail a letter without a street address (envelope motif, series continuity).**
   176→   - Fit: EP1's envelope = packet; DNS is the step *before* the first envelope can be addressed: the browser holds a blank envelope until the name becomes a number. The lookup traffic itself is tiny envelopes (UDP packets) running errands ahead of the big delivery.
   177→   - Distortion: postal directories are published centrally; DNS lookups are conversations between programs that can fail, retry, time out, or be answered from memory; and DNS does more than web pages (mail routing MX, reverse lookups PTR) — the film focuses on the web path only.
